# EdgeBox v0.1 Delivery Plan

## Delivery rule

Current live follow-up, 2026-10-15: the owner explicitly authorized the first
client -> existing VPS -> N1 residential egress deployment after Phase 2C.
The scoped data executor and VLESS client entry have actual desktop TCP/UDP
and management-survival evidence. This authorization supersedes historical
Phase 3 deployment blocks below for this specific increment, not the remaining
v0.1 acceptance requirements. See [live evidence](audits/2026-10-15-live-egress.md)
and [current operations](EGRESS_RUNBOOK.zh-CN.md). Web node integration and
whole-appliance qualification remain incomplete.

Work proceeds by safety gates, not feature count. A phase may produce code and namespace/VM evidence without authorizing live target deployment. No risky route, nftables, SSH, DNS, interface, or systemd-networking change is made on the remote appliance until current state is captured, rollback exists, and management survival is demonstrable.

## Phase 0 — repository and host audit

**Status:** documentation complete; live host unchanged.

Completed observations:

- repository contained only `AGENTS.md`; no Git metadata, code, tests, documentation, or legacy scripts were present;
- target is a Phicomm N1 running ARM64 Armbian/Debian 13;
- NetworkManager/netplan owns networking and systemd-resolved owns DNS;
- Ethernet uses DHCP for IPv4 and IPv6 with the ordinary default routes in the main table;
- no non-default policy rules, active WireGuard interface, or traffic-control class is present;
- an inactive experimental WireGuard configuration exists and is not an architecture contract;
- persisted nftables globally flushes the ruleset and installs broad masquerading, both requiring careful migration rather than reuse;
- current access is direct root/password SSH, with no verified reverse-management survival path.

The detailed, redacted evidence is in [the dated host audit](audits/2026-09-23-edgebox-host.md).

**Exit gate:** architecture, failure model, remote-management design, phased plan, and host evidence are reviewed. Before any live mutation, a bastion endpoint, unique credentials, port allocation, rollback implementation, and an explicit maintenance procedure must exist.

## Phase 1 — minimal Go foundation

Deliver:

- a Go module and `cmd/edge-agent` executable;
- concrete configuration types with validation and secret references;
- explicit state machine and transition tests;
- structured `log/slog` logging suitable for journald;
- structured health model;
- minimal transport, network transaction, and management-observer interfaces used by real orchestration code;
- filesystem state-store contract for factory/current/previous configurations and transaction journals.

Avoid empty package trees. Prefer standard library dependencies unless an external package materially reduces risk.

Tests:

- unit tests for configuration validation and transition legality;
- atomic persistence/crash-recovery tests using temporary directories;
- logging tests demonstrating secret fields are not emitted;
- architecture checks that management observation is independent from transport state.

**Exit gate:** `go test ./...` and static analysis pass on the development machine; cross-compilation for `linux/arm64` succeeds; no target networking changes occur.

## Phase 2 — reverse SSH management

Deliver:

- installation/rendering assets for a unique-key `edge-management.service`;
- bastion hardening example and static port registry format;
- management health observation in `edge-agent` without process ownership coupling;
- operator runbook and key-rotation/revocation procedure;
- timed rollback procedure for SSH hardening.

Tests in an isolated VM/container-network lab:

- loopback-only bastion binding;
- wrong port/key cannot create a listener;
- no tunnel-account shell, local forwarding, agent forwarding, X11, or PTY;
- reconnect after SSH process kill, bastion restart, WAN disconnect, DNS interruption, and address renewal;
- data-plane service/agent crash does not terminate the management service.

**Live exit gate:** a fresh operator login through the reverse path succeeds after forced reconnect. Only then may password SSH hardening be attempted under a timed rollback.

## Phase 3 — WireGuard Transport V1

Blocked pending Phase 2C qualification. Do not deploy the live data plane during
the management AP/Web/OTA milestone.

Deliver:

- generic transport lifecycle and packet-endpoint contract;
- isolated WireGuard implementation with key-file references, peer endpoint, allowed transport addresses, persistent keepalive, and configured/effective MTU;
- configuration rendering and process/interface health without NAT or policy-routing side effects;
- restart and stale-handshake policy with bounded backoff.

Tests:

- configuration validation and secret redaction;
- interface create/reconcile/remove idempotency in a network namespace;
- peer restart, endpoint loss, stale handshake, address change, and repeated apply;
- proof that WireGuard code does not manipulate generic nftables or policy routing.

**Exit gate:** namespace/VM transport tests pass and management remains independent. No MASQUE or custom QUIC work begins.

## Phase 4 — IPv4 egress network transaction

Deliver:

- immutable desired network plan and durable transaction journal;
- dedicated routing table/rule ownership for explicitly classified forwarded traffic;
- atomic isolated `inet edgebox` nftables batch for forwarding and IPv4 masquerade;
- explicit MTU propagation and simple bandwidth ceiling in the generic network layer;
- exact rollback and reconciliation after interruption.

Tests:

- repeated apply and nftables semantic idempotency;
- unrelated nftables tables survive apply and rollback;
- invalid batch does not partially apply;
- routing rollback, agent crash mid-transaction, and simulated power loss;
- forwarded traffic exits the WAN while local SSH/DNS/HTTPS remains on `main`;
- return traffic succeeds through conntrack/NAT;
- configured bandwidth ceiling is enforced within documented tolerance.

**Live exit gate:** remote application remains blocked until the reverse-management path is proven and an external watchdog can trigger rollback.

## Phase 5 — verification, rollback, and SAFE_MODE

Deliver:

- complete validate/prepare/apply/verify/commit workflow;
- automatic timeout/crash rollback;
- failure counters and explicit SAFE_MODE entry/recovery;
- exact cleanup of EdgeBox-owned routing, nftables, and shaping state;
- preserved factory, previous known-good, and current configurations.

Tests:

- bad network configuration rollback;
- failed WAN, DNS, management, transport, NAT, and egress verification paths;
- SAFE_MODE entry is idempotent;
- SAFE_MODE preserves ordinary WAN and management service while disabling data plane;
- controlled recovery does not flap or reboot-loop.

## Phase 6 — health, telemetry, packaging, and target qualification

Deliver:

- structured per-domain health and low-volume telemetry;
- systemd unit and installation layout for `edge-agent`;
- ARM64 build/release artifact and checksums;
- journald operator procedures and redaction review;
- reproducible target qualification runbook.

Qualification scenarios:

- cold boot and repeated reboot;
- WAN cable loss/recovery and DHCP renewal;
- relay and WireGuard restart;
- agent crash and interrupted apply;
- management tunnel reconnect;
- repeated apply and rollback;
- SAFE_MODE entry/recovery;
- sustained proof that data-plane failure does not unnecessarily kill management access.

## Deferred beyond v0.1

MASQUE/CONNECT-IP research, automatic transport switching, relay optimization, complex control backends, billing, geo-routing, Kubernetes, full IPv6 egress, and live A/B root filesystem updates remain explicit non-goals. The approved Phase 2C extension adds offline Web management and application OTA; whole-system OTA remains research only.

## Immediate next phase

Phase 2C is in progress. Management stabilization has real fresh-login evidence;
the isolated AP and DHCP passed reboot recovery, and iPhone authentication/DHCP
passed after disabling PMF on the owned profile. Web and its independent updater
are running and enabled with a privately provisioned owner password. Mobile
dashboard/password-change/offline qualification and live OTA tests remain open. Do not move past a
milestone's deployment gate without its real tests. See [current evidence and
remaining gates](PHASE_2C.md).
